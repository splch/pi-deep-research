## 1. Executive summary

1. **Decompose into three phases**: scoping → iterative research → synthesis. All four production systems (OpenAI, Anthropic, Google, Perplexity) and all surveyed open-source frameworks follow this shape ✓ [1][8][9][13][29][30][31].
2. **Choose a topology deliberately**: orchestrator-worker (Anthropic) for breadth-heavy, parallelizable problems; single-agent RL (OpenAI) when you can afford to train end-to-end; planner-with-async-tasks (Google) when you need durable session state; supervisor-with-isolated-subagents (LangGraph) when you need an open-source production stack ✓ [1][9][29].
3. **Encode effort scaling in the prompt**: Anthropic's lead agent is told to use 1 agent / 3–10 calls for fact-finding, 2–4 subagents / 10–15 calls for comparisons, and 10+ subagents for complex research — preventing pathological over-decomposition ✓ [1][2][3].
4. **Layer hard caps with soft stopping rules**: ReAct used a hard 7-step cap on HotpotQA; modern systems combine that with reflection-driven stopping (`think_tool` / Self-RAG's `Retrieve` token / Reflexion's evaluator) ✓ [17][18][19][21][29].
5. **Compress between stages, not just at the end**: deliver compact "findings/learnings" up the agent tree, not raw page dumps; keep raw content in worker-local context ✓ [27][28][29][30].
6. **Make retrieval iterative and adaptive**: Self-RAG's per-segment δ threshold and Anthropic/Google's planner-driven re-querying both outperform single-shot RAG; corpus-side test-time augmentation closes much of the gap when retrievers are off-the-shelf ◐ [19][20][33].
7. **Treat citation faithfulness as a first-class metric**: separate "citation association" (every claim cited) from "citation accuracy" (citation actually supports claim), and use an **LLM ensemble** judge — LiveResearchBench's DeepEval found single-judge Likert prompts <60% human-aligned ◐ [35].
8. **Block the "lethal trifecta" architecturally**: disallow arbitrary URL construction, sandbox the Python tool with no internet egress, and rate-limit outbound communication — this is the explicit OpenAI mitigation pattern ✓ [5][6][7].

## 2. Reference architectures

### 2.1 Single-agent RL loop — OpenAI Deep Research

OpenAI Deep Research is **a single agentic model** — described as "an early version of OpenAI o3 optimized for web browsing" — trained end-to-end via reinforcement learning on browsing tasks (search/click/scroll/file-reading) plus a sandboxed Python tool with no internet access ✓ [5][6][7][8]. There is **no parallel subagent fan-out**; capability scales with test-time compute and a "max tool calls" parameter, with internal expert-task evals showing pass-rate increases monotonically with that budget ✓ [7]. A second, custom-prompted **o3-mini** summarizes the chain of thought shown to the user — this is OpenAI's only documented model cascade ✓ [5][6]. Wall-clock per query is 5–30 minutes; the Feb 2026 update added MCP/app connectors and trusted-site restriction ✓ [8].

### 2.2 Orchestrator-worker — Anthropic Claude Research

The most-documented multi-agent architecture in the field. A **LeadResearcher** (Claude Opus 4) decomposes the query, persists a plan to an external **Memory store** (to survive 200K-token context truncation), then spawns **3–5 subagents** (Claude Sonnet 4) in parallel; each subagent runs its own OODA loop with **3+ tools called in parallel** within its own context window. A separate **CitationAgent** runs at the end to attribute claims to sources ✓ [1][2][3][4]. Effort scaling is hard-coded in prompts (see §3). Lead agents currently invoke subagents **synchronously** — a known bottleneck Anthropic has flagged as a future direction ◐ [1][3].

### 2.3 Planner + asynchronous task manager — Google Gemini Deep Research

Architecturally closer to Anthropic in spirit but uses a **single planner** that orchestrates concurrent task models rather than spawning autonomous agents. Components: (i) a multi-step planner that produces a **user-editable** research plan; (ii) task models that the planner schedules — "intelligently determines which sub-tasks can be tackled simultaneously and which need to be done sequentially"; (iii) a synthesis stage with self-critique passes ✓ [9][12]. A novel **asynchronous task manager** maintains shared state between planner and task models so single failures don't restart the run ✓ [9]. Combines Gemini's 1M-token context with a RAG layer to retain hundreds of pages browsed within a session ✓ [9][11]. The April 2026 release split into two SKUs — "Deep Research" (low-latency interactive) and "Deep Research Max" (extended test-time compute, asynchronous) — both on Gemini 3.1 Pro ◐ [11].

### 2.4 Single-agent + production retrieval stack — Perplexity Deep Research

Perplexity Deep Research (launched Feb 14, 2025) is publicly described as a single-agent iterative loop that "performs dozens of searches, reads hundreds of sources, and reasons through the material," typically completing in **2–4 minutes** per query — substantially faster than OpenAI/Google ✓ [13][14]. The retrieval substrate (April 2026 engineering post) uses **hybrid keyword+semantic retrieval, multi-stage ranking** (a fast recall step in 100–200 ms followed by slower rerankers), and a "content understanding" module that segments pages into spans used as first-class retrieval units ◐ [16]. Post-training is two-stage (instruction/tool behavior, then harder search/synthesis) with rubric-based rewards plus a **discipline term that penalizes search steps and tokens that don't measurably improve the answer** ◐ [15].

### 2.5 Open-source patterns

- **LangGraph Open Deep Research** (production reference for the supervisor pattern): supervisor bound to three tool schemas — `think_tool`, `conduct_research`, `ResearchComplete` — using a manual tool-execution pattern; `conduct_research` spawns **isolated parallel research subgraphs whose results return as compact summaries**, explicitly to avoid context bloat in the supervisor ◐ [29].
- **Hugging Face Open Deep Research** (smolagents): manager `CodeAgent` (`max_steps=12`, `planning_interval=4`) delegates to a `search_agent` `ToolCallingAgent` (`max_steps=20`, `planning_interval=4`); rationale is that **code-actions take ~30% fewer steps than JSON tool-calls** ✓ [24][25].
- **GPT-Researcher**: recursive tree with `DEEP_RESEARCH_BREADTH` (default 3–4), `DEEP_RESEARCH_DEPTH` (default 2), `DEEP_RESEARCH_CONCURRENCY` (default 4 asyncio semaphore); breadth halves and depth decrements per level ✓ [26][27][28].
- **Static-DRA** (configurable hierarchical static plan): Tavily relevance-score threshold of 0.30, top-5 results per query ◐ [32].

## 3. Planning & decomposition

### 3.1 Foundational scratchpad and step-cap patterns

**ReAct** established the interleaved Thought/Action/Observation scratchpad where thoughts decompose goals ("I need to search x, find y, then find z"), track sub-goal progress, and reformulate failed queries ✓ [17][18]. ReAct also pioneered **empirically-chosen hard step caps** (7 for HotpotQA, 5 for FEVER, beyond which accuracy plateaued) and a fallback rule: when ReAct exhausts its steps, back off to CoT self-consistency; conversely back off to ReAct when CoT-SC majority is below n/2 ✓ [17]. The most common ReAct failure mode is reasoning-loop / repetitive thoughts (~47% of HotpotQA failures), with non-informative search at ~23% — directly motivating tree-search successors ◐ [17].

### 3.2 Tree search and reflective memory

**Tree of Thoughts** generalized step-level reasoning to deliberate **BFS/DFS search over coherent text units**, with an LLM-as-evaluator (value or vote scoring) to prune branches and explicit branching-factor and depth hyperparameters ✓ [23]. **Reflexion** layered an episodic verbal-RL memory: actor (often a ReAct agent) + evaluator + self-reflection generator that writes critiques into an episodic buffer; trials repeat up to a configurable `num_trials` cap. The reference implementation exposes four memory strategies — `NONE`, `LAST_ATTEMPT`, `REFLEXION`, `LAST_ATTEMPT_AND_REFLEXION` — letting practitioners ablate short-term trajectory vs. long-term reflective memory ✓ [21][22].

### 3.3 Adaptive per-segment retrieval — Self-RAG

**Self-RAG** replaces the global "should-I-retrieve" decision with **per-segment reflection tokens**: the model emits `Retrieve ∈ {yes, no, continue}` segment-by-segment, and a configurable threshold **δ on the normalized P(Retrieve=Yes)** lets users tune retrieval frequency without retraining ✓ [19][20]. Inference uses **segment-level beam search** (beam size B over K passages) with scores combining critique tokens `ISREL`/`ISSUP`/`ISUSE` — a soft, multi-criterion stopping/selection rule rather than a global counter ✓ [19].

### 3.4 Effort scaling in production

Anthropic's lead-agent prompt encodes explicit effort tiers ✓ [1][2][3]:
- Simple fact-finding: **1 agent, 3–10 tool calls**
- Comparisons: **2–4 subagents, 10–15 calls each**
- Complex research: **10+ subagents** with clearly divided responsibilities
- Typical run: 3–5 subagents in parallel, each running 3+ tools in parallel

GPT-Researcher exposes the breadth/depth knobs explicitly and **decays them**: at each recursion level, `new_breadth = max(2, breadth // 2)` and `new_depth = depth - 1`, with the next-level query constructed from the previous research goal plus model-generated follow-up questions ✓ [28]. Additional caps: `MAX_ITERATIONS=3` (query expansion), `MAX_SUBTOPICS=3`, `MAX_SEARCH_RESULTS_PER_QUERY=5`, plus a coarse `reasoning_effort = low/medium/high` knob ✓ [26].

LangGraph Open Deep Research uses a **layered stopping rule**: the supervisor calls `think_tool` before every decision and emits `ResearchComplete` when reflection deems coverage sufficient, with a hard `research_iterations` counter as a backstop ◐ [29]. Sub-agents independently call their own `research_complete` when their topic is exhausted ◐ [29].

### 3.5 Cross-system recommendations

Triangulating across primary sources, the following recommendations recur ✓ [27][28][29][30][31]:

1. Make breadth and depth **explicit configurable hyperparameters** and decay them over recursion.
2. Separate scratchpad (raw thought/action/observation within a step) from long-term memory (compressed learnings, reflections, citations); pass only compressed form upward.
3. Combine a **hard step cap** with a **soft reflection stopping rule**.
4. Use a `planning_interval` (smolagents = 4) to **re-plan periodically**, not only at the start.
5. Summarize/compress retrieved content **before** storing it in working memory.
6. Sub-agents return **findings (information), not finished prose** — let the final writer compose from raw learnings for coherence.
7. Provide a soft retrieval/budget knob (Self-RAG δ; `reasoning_effort`) for user-driven cost/quality tradeoff.

## 4. Retrieval & browsing

### 4.1 The four-stage agentic pipeline

The Zhang et al. survey codifies the canonical pipeline as **Planning → Question Developing → Web Exploration → Report Generation**, with retrieval iterative and agent-driven rather than single-shot ✓ [31]. Frontier systems split between API-based search backends (Bing for OpenAI, Google for Gemini, Bing+Sonar BM25/keyword/dense rerank for Perplexity) and **agentic browsers** — Selenium/Playwright DOM agents and multimodal vision-language agents (WebVoyager, MM-ReAct) for JS-rendered or visually complex pages ✓ [31].

### 4.2 The BM25 vs. reasoning-retriever debate

Two recent papers in our source set come to different conclusions about retrieval-stack design — a substantive disagreement worth flagging:

- **SAGE** finds that for current deep-research agents, **BM25 still beats reasoning-tuned LLM retrievers** (ReasonIR, gte-Qwen2-7B) by ~30% on scientific retrieval, because agents emit short keyword-oriented sub-queries; the proposed fix is **corpus-side test-time augmentation** (LLM-generated metadata/keywords on documents) rather than fancier retrievers ◐ [33].
- **AgentIR** pushes the opposite direction: embedding the agent's natural-language reasoning trace alongside the query lifts an open-weight agent on BrowseComp-Plus from 37% (BM25) and 50% (conventional embeddings) to **68%** ◐ [34].

Sources differ on retrieval stack design: [33] argues for **corpus-side augmentation when retrievers are off-the-shelf**, [34] argues for **retriever-side reasoning-aware embeddings when you can co-train**. The two are partly reconcilable (different scopes) but imply different design recommendations.

### 4.3 Query rewriting and decomposition as a learned skill

Query Developing is now treated as a learnable module. Two paradigms ✓ [31]:

- **Reward-optimized RL agents**: DeepResearcher, Search-R1, R1-Searcher, ZeroSearch, DeepRetrieval, MaskSearch — trained with binary format rewards plus token-F1 or Recall@K/NDCG@K; richer multi-dimensional rewards (InForage, OTC-PO, IKEA, AutoRefine, R-Search) penalize redundant tool calls or reward information gain.
- **Supervision-driven**: ManuSearch, Search-o1, SearchAgent-X for multi-agent decomposition; ReasonRAG uses MCTS+DPO over reasoning trajectories.

### 4.4 Practical filtering, dedup, freshness

- **Relevance threshold before context entry**: Static-DRA uses a **0.30** Tavily relevance cutoff and keeps the top 5 results ◐ [32].
- **Compression before passing context up**: every framework surveyed deduplicates, reranks, refines, and consolidates retrieval into structured learnings/findings before passing to the report generator ✓ [29][30][31].
- **Freshness via task design**: LiveResearchBench requires tasks to be **time-varying** (with `{{date}}` placeholders resolved at evaluation time) so static, contamination-prone benchmarks score lower ◐ [35].
- **Multi-round progressive search**: a converging best practice across closed-source (OpenAI, Gemini, Perplexity, Grok, Qwen) and open-source (DeerFlow, dzhng, langchain, scira, OpenDeepSearch) implementations, rather than emitting a single batch of keyword queries ✓ [30].

### 4.5 Page-extraction stack

Practical systems combine ✓ [31]:
- Static HTML: Scrapy, BeautifulSoup
- DOM/JS-rendered: headless Selenium, Playwright
- Visually complex: multimodal screenshot+HTML agents (WebVoyager achieves 59% task success using GPT-4V; MM-ReAct embeds screenshots in reasoning chains)

## 5. Grounding & citations

### 5.1 Citation styles

The dominant inline style — bracketed numeric citations at sentence end, statement-level granularity, typically **≤3 citations per statement** — appears across the surveyed systems ✓ [31][35]. Anthropic's pipeline assigns citation generation to a **separate CitationAgent** that runs after synthesis ✓ [1][2][3].

### 5.2 Faithfulness rubrics in production

**LiveResearchBench's DeepEval** ◐ [35] is the most concretely documented production-style citation evaluator in our source set. Key design choices:

- **Separate two metrics**: "Citation Association" (whether every claim has *some* citation, scored 0–100 with deductions for missing/misplaced citations) vs. "Citation Accuracy" (whether the cited URL substantiates the claim).
- **Agentic rubric-tree** for hallucinated-citation detection. For each (claim, URL) pair, check:
  - **E1**: URL resolves
  - **E2**: URL is topically relevant
  - **E3**: content actually supports the claim
- **LLM ensemble judge** (Gemini 2.5 Pro + GPT-5) — adopted after finding single-rubric Likert prompts <60% human-aligned and Claude 4 Sonnet "inconsistent and low agreement with human experts" as a citation judge.

On the most search-intensive tasks, top systems (GPT-5, Grok-4 Deep Research, Open Deep Research) still produce **19–92 citation errors per report**, dominated by **E3 unsupported-claim** hallucinations ◐ [35].

### 5.3 Recurring citation/browsing failure modes

LiveResearchBench documents the following failure modes recurring across systems ◐ [35]:

- Mismatched in-text citations and references
- Missing/incomplete URLs (or provider-redirect "grounding" URLs that inflate token counts but not coverage)
- Inconsistent citation formats
- Uncited references appearing only in the bibliography
- Broken table formatting
- Out-of-order reference numbering
- Embedded citations breaking text flow
- Outright fabricated facts

### 5.4 The deep-searcher vs. deep-researcher distinction

LiveResearchBench observes that **multi-agent systems lead on Citation Association and Presentation, while single-agent web systems lead on Factual & Logical Consistency** (because of one persistent memory stream); **most current "deep research" systems behave more like deep searchers (information collectors) than deep researchers (insight synthesizers)** — only Deerflow+ and Gemini Deep Research outperform Open Deep Research on analysis depth in its evaluation ◐ [35].

## 9. Open problems & disagreements

### 9.1 Multi-agent vs. strong single-agent

Sources visibly disagree on whether multi-agent orchestration is architecturally superior or merely a more compute-intensive default:

- **Pro multi-agent**: Anthropic's own reported 90.2% lift over single-agent Opus 4 on its internal research eval ✓ [1][2][3].
- **Skeptical**: Anthropic itself acknowledges that **token usage alone explains ~80% of BrowseComp variance** and that lead agents currently invoke subagents synchronously — both findings consistent with the view that much of the multi-agent advantage comes from extra compute rather than architecture ◐ [1][2][3].
- **Empirical evidence on the broader literature** (head-to-head, compute-matched studies) is referenced in the brief and discussed widely, but cannot be cited from our numbered source set without inventing references. **Flagged as evidence-thin in this report.**

### 9.2 Synchronous vs. asynchronous orchestration

A **genuine engineering choice difference**, not source disagreement: Anthropic explicitly says today's lead agents call subagents synchronously (the lead can't steer mid-flight; the run blocks on the slowest subagent) ◐ [1][3], while Google describes its task manager as asynchronous with shared state ✓ [9].

### 9.3 Retrieval stack: BM25 vs. reasoning embeddings

See §4.2 — [33] favors corpus-side augmentation, [34] favors retriever-side reasoning-aware embeddings; recommendations diverge.

### 9.4 Citation evaluation framework

Sources [33], [34], and especially [35] adopt different evaluation philosophies; LiveResearchBench's authors explicitly argue holistic LLM-as-judge ratings and single-rubric Likert prompts both fall below 60% human agreement, motivating their structured rubric tree + ensemble judge ◐ [35]. The community has not converged on a single faithfulness metric.

### 9.5 Iteration cap defaults

No standardization across implementations:
- ReAct: 7 (HotpotQA) / 5 (FEVER) ✓ [17][18]
- HF Open Deep Research: `max_steps=12` (manager) / `max_steps=20` (search) with `planning_interval=4` ✓ [24][25]
- GPT-Researcher: `MAX_ITERATIONS=3` (query expansion); recursion depth=2 ✓ [26][27]
- LangGraph Open Deep Research: configurable `research_iterations` without publicly stated default ◐ [29]

Sources do not agree on a single recommended cap; the best you can do is benchmark on your task distribution.

### 9.6 HLE score comparability

OpenAI Deep Research 26.6% (Feb 2025) vs. Perplexity Deep Research 21.1% (Feb 2025) vs. Gemini Deep Research 46.4% (Dec 2025) are **not directly comparable** — each was run at a different point in time on evolving benchmark/test sets, with different scaffolding/tool budgets ✓ [5][6][9][13]. This is a temporal/methodology gap, not a contradiction, and the source posts do not normalize.

### 9.7 Long-context vs. RAG

The brief asks about disagreement on when long context replaces RAG. Google explicitly **combines** Gemini's 1M-token context with a RAG layer rather than choosing ✓ [9][11]; Anthropic uses an **external Memory store specifically because** 200K context still truncates on multi-step research ◐ [1][2][3]. This suggests in practice **both** are needed, but our source set doesn't contain a dedicated long-context-vs-RAG ablation.

## 10. Concrete checklist — if you're building one tomorrow

1. **Pick a topology and document why**: orchestrator-worker (Anthropic-style) for breadth-heavy parallelizable problems; single-agent + RL for end-to-end-trainable scope; planner + async tasks for durable session state ✓ [1][5][9][29].
2. **Three-phase pipeline**: scoping → iterative research → synthesis, with the scoping output as the **only context** passed downstream ✓ [29][30][31].
3. **Encode effort tiers in the lead-agent prompt**: 1 agent / 3–10 calls (fact-finding), 2–4 / 10–15 (compare), 10+ (complex) ✓ [1][2][3].
4. **Decay breadth over recursion** (`max(2, breadth // 2)`); decrement depth ✓ [27][28].
5. **Layered stopping rules**: hard step cap (ReAct's 7 / smolagents' 12–20) + soft reflection (`think_tool` / Self-RAG δ / Reflexion evaluator) ✓ [17][19][24][29].
6. **Periodic re-planning**, not just at the start (`planning_interval=4` in smolagents) ✓ [24][25].
7. **Compress between stages**: workers return findings/learnings (compact), not raw page dumps; supervisor keeps a summary of subagent outputs, not their full message history ✓ [27][28][29][30].
8. **Hard scratchpad cap with most-recent-wins trimming** (e.g., 25,000 words) ✓ [27][28].
9. **Hybrid retrieval with multi-stage rerank**: keyword + semantic + reranker, with a relevance-score threshold (e.g., 0.30) before context entry ✓ [16][32].
10. **Adaptive per-segment retrieval** when feasible (Self-RAG δ); avoid one-size-fits-all retrieval frequency ✓ [19][20].
11. **Separate CitationAgent / citation-pass at end**: don't ask the synthesis model to cite while drafting ✓ [1][2][3].
12. **Two citation metrics**: Citation Association (every claim cited?) and Citation Accuracy (citation actually supports claim?), evaluated with an **LLM ensemble** judge — single-rubric Likert prompts <60% human-aligned ◐ [35].
13. **Structured rubric tree for hallucinated-citation detection**: E1 URL resolves, E2 topically relevant, E3 actually supports ◐ [35].
14. **Block the lethal trifecta architecturally**: disallow arbitrary URL construction, sandbox the Python tool with no internet egress, use trusted-site lists for connectors ✓ [5][6][7].
15. **Evaluation discipline**: small-N (~20) for fast iteration, LLM-judge for scale, **human eval** to catch source-quality biases (SEO farms ranked over academic PDFs); report pass@k *and* cons@k for variance ✓ [1][5][6].
16. **Operational hygiene**: rainbow deployments for in-flight agents; durable external memory (Anthropic's external store / Google's async task manager); rate limit aggressively at launch ✓ [1][7][9].
